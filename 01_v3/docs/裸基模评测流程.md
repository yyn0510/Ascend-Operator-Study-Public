# CANN-Bench 五轮三轨迹平台反馈评测流程（V3）

## 一、先理解研究对象和当前状态

### 1.1 研究的是哪一种能力

让基础模型根据给定算子任务、工程规则和固定示例生成完整Ascend C实现，再由外部程序送往昇腾NPU平台评测。模型根据平台反馈继续改写，观察固定预算下的交付质量、正确性、性能和稳定性。

这里的“裸基模／tool-free”指模型不主动使用终端、搜索、文件编辑、编译器或平台工具。**模型有反馈，但反馈由外部Harness取得和整理。** 因而它既不是完全无反馈的一次生成，也不是能自主探索环境的编码Agent。

| 角色                     | 负责什么                                |
| ---------------------- | ----------------------------------- |
| 生成模型                   | 根据任务与反馈输出当前完整五文件和改动简述               |
| Harness                | 提示装配、API调用、格式解析、工程装配、提交、轮询、反馈和归档    |
| BenchSite／CANN-Bench平台 | 实际构建与执行，检查精度并测量性能，返回分项结果            |
| 研究者                    | 设计规则、运行与恢复实验、审计例外及分析结果；归档中的人工结案另行披露 |

任务基于CANN-Bench，流程框架参考算子生成评测中的统一给题、外部执行和迭代反馈思路。V3流程本身不定义新算子数学公式，也不训练新的多模态模型。

### 1.2 已完成与未完成

正式主集合是A3平台、Level1八算子、九个完整模型，共：

`9模型 × 8算子 × 3轨迹 × 5轮 = 216条完整轨迹、1080个round_completed轮次。`

真实多模态模型算子替换已完成，结果见本资料包第二部分；这些应用测试不计入V3的1080轮。V2十轮试跑、V3 smoke及下一版Agent Harness均排除在本主集合之外。

## 二、实验单位：三个独立起点，每个五轮

每个“生成模型×目标算子×平台”运行三条轨迹：

```text
trajectory_001：R1 → 反馈 → R2 → 反馈 → R3 → 反馈 → R4 → 反馈 → R5
trajectory_002：R1 → 反馈 → R2 → 反馈 → R3 → 反馈 → R4 → 反馈 → R5
trajectory_003：R1 → 反馈 → R2 → 反馈 → R3 → 反馈 → R4 → 反馈 → R5
```

- 各轨迹不共享生成代码、反馈或对话上下文。
- 设计目标是同一模型、同一任务、同一平台的三条R1提示一致。实际发现的GLM例外见第六节。
- 托管接口未提供可验证的确定性seed，记录为`provider_unseeded_independent_trajectories`。temperature为0也不被当作确定性保证。
- 一旦进入有效轮次，正常内容质量差不另抽一个候选；模型内容失败按规则消耗该轮。
- 已编译、已有非零分或已经全正确都不提前结束；轨迹固定到R5。

三轨迹提供多个独立起点，五轮提供轨迹内的反馈机会。它们承担不同作用：增加同一路径的轮数不等于增加独立起点。本设计没有同预算“15次独立生成”对照，不直接证明三轨迹五轮优于其他预算分配。

### 轮次、API请求和平台作业不是同一个数

每模型×算子有15个正式生成轮次，每完整模型120轮。正常情况下每轮最多一次新平台提交，但：

1. 格式不可恢复时不提交。
2. 与上一轮源码相同且满足复用条件时，不创建新平台作业。
3. 网络重试可让同一轮发生多个API传输尝试。
4. 历史基础设施重提可让同一份源码对应多个平台job，仍不增加模型轮次。
5. 预算用完、网络故障或账号限制造成的未完成状态不自动成为已完成轮次。

因此“1080轮”不是“1080次独立NPU性能测量”或“恰好1080次API请求”。

## 三、模型最初接收的材料与输出约定

### 3.1 初始材料

初始提示版本为`iterative_one_shot_add_v3`，通常包含：

- 平台profile与批次冻结快照：目标硬件标签、工程架构、CANN、PyTorch和torch_npu版本。
- 当前任务的`proto.yaml`、`desc.md`、`golden.py`与`cases.yaml`内容。
- 统一Direct Launch工程契约、允许输出文件及五轮规则。
- 固定公共Add算子的完整五文件one-shot，说明工程写法与接口组织。
- 完整文件边界和CHANGE SUMMARY格式。

目标任务材料本身含参考语义及测试输入定义。因此不能称为“只给一句自然语言描述”或“完全看不到测试条件”。设计不额外给目标算子的专属API卡、人工算法路线、历史错误修复提示。**任务说明和golden是输入信息，不等于要求照搬其高层参考实现作为生成内核。**

协议设置`baseline_performance_in_initial_prompt=false`。成功轮之后可以给代表用例的baseline耗时与硬件下界；不要把“初始不提供性能锚点”与“全程不提供baseline信息”混淆。

八个任务为：Exp、ForeachAddcdivScalar、ForeachNorm、GELU、MaskedScale、Mish、Sigmoid、SwiGLU。它们是具有视觉/多模态应用位置的通用计算子集。各任务覆盖条件以自己的任务文件为准，不把集合覆盖误写成每个算子均有全部属性/dtype组合。

### 3.2 五文件契约

对算子`<op>`，顺序固定为：

```text
csrc/ops/<op>/op_kernel/<op>_kernel.cpp
csrc/ops/<op>/op_kernel/<op>_launch.h
csrc/ops/<op>/op_plugin/<op>_plugin.cpp
csrc/ops/<op>/CMakeLists.txt
cann_bench/__init__.py.append
```

每个文件按`=== FILE: 路径 ===`、正文、`=== END FILE ===`输出。每轮都是完整快照，不是diff，不依赖Harness为其补齐未输出的算法。

五文件之后是`=== CHANGE SUMMARY ===`和`=== END CHANGE SUMMARY ===`之间的一段不超过300个Unicode字符的简述。它不是第六个源码文件，也不是要求输出思维链。**缺失或超长按格式违规记录；只要五文件可安全恢复，并不因此阻断提交。** 不能把简述缺失一律记为“无法评测”。

## 四、R2–R5到底看到什么

### 4.1 滚动上下文

常规请求消息形态为：

```text
user      ：冻结的初始提示与任务材料
assistant ：上一轮model_output.txt原文（也可能是格式失败的输出）
user      ：上一轮feedback_prompt.txt
user      ：当前轨迹历轮尝试记录（若存在）
user      ：条件触发的长耗时提醒／严格格式提醒（若存在）
```

V3不是把所有R1至上一轮的完整对话无界拼起来。较早轮次只以机械尝试记录参与，保留上一轮原始输出和上一轮反馈。

通用协议的尝试记录上限12000字符，请求总内容上限500000字符；超过请求上限时停止报错，当前实现不是静默删减目标源码来凑长度。尝试记录按固定规则截断并带标记。这些是字符预算，不是token预算。

### 4.2 历轮尝试记录

`build_attempt_log()`按连续已完成状态从R1遍历，记录：

- 模型自己的简述（明确是模型声明）。
- 与相邻可比较版本的文件变化。
- 平台结果、错误指纹、源码哈希和一致性标记（机械生成）。

某轮格式失败、没有可比较源码时，该轮的简述、失败阶段和结果仍可保留；缺少源码比较不应截断后续已完成轮次。`change_summary_consistency`检查的是有简述时源码是否变化，并不是验证简述中每句话的语义真实性。

### 4.3 条件提醒与历史初始提醒

当前代码支持两种后续提醒：

- 上一轮生成耗时超过配置阈值时，提醒精简思考并尽快交付完整五文件。已启用批次常用阈值1200秒，未启用批次不会自动补发。
- 上一轮`format_recovered=true`且`strict_protocol_pass=false`时，提醒遵守严格文件格式。

这些都是模型实际输入的一部分。严格格式提醒不同于重新提供算法帮助；长耗时提醒仍可能改变生成行为，不能从流程描述中省去。

此外GLM历史批次还向初始提示追加过精简思考提醒，当前代码中相应metadata写固定false并不证明历史没用。实际出现范围见第六节。

## 五、每轮执行：解析、装配、提交和反馈

### 5.1 常规顺序

1. 检查当前轮是否已经`round_completed`；恢复时不重新生成已完成轮。
2. 渲染请求，保存精确消息与metadata，检查请求字符上限。
3. 调用模型；按协议处理传输/供应端异常，保存聚合响应、用量和输出。
4. 提取五文件与CHANGE SUMMARY，保存解析报告与恢复标记。
5. 不可恢复时形成格式反馈及0分内容失败，不送平台。
6. 可恢复时机械装入固定脚手架副本，检查与上一轮的源码复用条件。
7. 不复用则私有提交BenchSite，保存job_id并轮询终态；检查运行环境。
8. 按阶段确定性生成反馈，记录分数、通过数及审计状态。
9. 写`status=round_completed`；R1–R4为下一轮生成反馈文本，R5保存反馈payload但没有实际R6。

### 5.2 严格格式与可恢复格式

`strict_protocol_pass`考察边界、顺序、残留文字、围栏、简述等是否严格符合协议。`recoverable_parse_pass`考察五个指定文件是否能安全识别：数量正确、无重复/缺失/额外路径、内容非空、文件块闭合。

宽松恢复可以识别部分边界空白差异、路径前缀或分隔符写法，按指定路径归位文件，去掉允许的外层围栏或忽略块外文字，记录顺序/简述违规。提取时统一尾部换行。它不能推断未输出的函数、补写缺失文件、修改Ascend C API或精度算法。

**特殊细节：**文件正文中的内部Markdown围栏会被记录，但解析器不自动删除它；源码仍可能被提交并编译失败。部分静态契约检查也是诊断项，不等于全部作为提交硬门槛。不要把“可恢复”写成“源码已通过静态正确性审查”。

### 5.3 工程装配的机械改动

装配程序复制公共脚手架，移除Add/Sqrt示例算子，清理示例Python导出，放入目标算子四文件并追加其Python包装。根据平台profile配置公共CMake中的架构映射，保存整个提交工程与哈希。

因此准确边界是**不修复生成算法源码**，不是“工程中的每个字节都不改变”。格式提取、导出拼接和平台构建映射属于事先定义的机械步骤。

### 5.4 相同源码复用

当前实现主要检查：阶段感知流程、可比较五文件哈希完全相同、上一轮目录存在平台结果。满足时复制上一轮结果并保存`evaluation_reuse.json`，反馈说明没有实际源码改动。

它不是跨模型、跨轨迹、跨版本任意缓存搜索，也不是新的性能复测。某些标志如`submitted=false`可能只表示本轮没创建新回执，不能据此认定格式失败。

本次主集合九模型**未发现复用记录**。此处区分实现能力与实际发生量。

### 6.4 人工结案与格式恢复的区别

GLM有3个已完成状态的`score_source`包含manual，均归档为未提交的0分格式失败：

- Exp T1/R5：长时间未形成可提交正文，按用户指示结束并归档。
- GELU T2/R5：两次空正文/length及供应端资源异常后人工裁定结束。
- GELU T3/R4：两次同payload空正文/length后，按人工规则未发第三次请求。

它们不是给源码人工补写API，但也不等同于全自动、完全同质的失败处理。涉及空输出、输出截断、资源中断和人为停止的混合归因应披露。分析是否需要敏感性说明可另行讨论，本次不重新裁决分数或修改原状态。

### 6.5 这些差异如何解释

可表述为：统一任务与预算框架下、既有实际调用配置的能力比较。实际存在采样/思考设置、条件提醒、模板或人工结案差异，因此不将总分差异直接解释为纯模型架构的因果差异。V3也不能被描述成“无任何人工运营的Agent自主实验”。

## 七、阶段感知反馈：具体哪些信息进入下一轮

反馈schema为`cannbench_iterative_feedback_v3`，当前实现函数沿用`build_platform_feedback_v2`名称。函数后缀不代表这些正式结果属于V2试跑。

| 阶段           | 给模型的信息                                                 | 固定省略的内容                     |
| ------------ | ------------------------------------------------------ | --------------------------- |
| 编译失败         | job摘要、最多3组根错误，每组最多2条紧邻note                             | 重复级联case、baseline、硬件下界和性能细节 |
| 正确性失败        | 通过数、最多5个失败case、可用的MERE/MARE等指标、最多3条去重运行错误              | 已通过case详情和性能锚点              |
| 其他运行/测试失败    | failed_stage或runtime、去重运行错误，必要时受影响case                 | 性能锚点和无关细节                   |
| 全部正确／成功终态    | 总分与分项、平均speedup、最低perf_score的最多3个case及耗时/baseline/硬件下界 | 原始平台大JSON、runner身份等         |
| 五文件不可恢复      | 缺失/重复/额外路径、边界/顺序/残留及简述诊断                               | 平台结果，因为本轮未提交                |
| 环境元数据缺失的零分例外 | 专门的平台fallback说明及已知失败信号                                 | 不伪造已通过环境验证或普通精度结果           |

排序规则是最低`perf_score`，不是最大张量、最慢绝对耗时或随机选择。精度失败里运行错误可能与数值错误混在一起，应按case字段进一步区分。

通用限制：每条错误最多1200字符，编译日志读取上限24000字符，反馈总上限12000字符。最终payload可能受固定裁剪影响，字段缺失不自动说明平台未产生该项。初始模型并不接收完整平台原始JSON。

模型能够用反馈定位和修改实现，但并不获得无限次自主测试。R5完成后没有新的模型轮次消费其反馈。

## 八、环境核验、恢复与零分例外

### 8.1 两层版本检查

提交前检查live runner与冻结profile/revision，不同可记warning；本轮结果返回后检查`setup_info.environment`中的CANN、PyTorch和torch_npu。`--skip-runner-verify`用于前者，不是通用跳过后者。

主实验归档正常运行时记录为CANN 9.1.0、PyTorch 2.9.0+cpu、torch_npu 2.9.0。平台请求标签为910c/A3；精确设备名称和工程架构必须按snapshot/profile保留，不能凭标签重新猜测芯片。版本字段吻合也不等于证明服务端所有实现代码、基线和编译器细节从未变化。

### 8.2 外部恢复

| 情况                  | 常规处理                       | 是否直接完成一个新模型轮次 |
| ------------------- | -------------------------- | ------------- |
| 有效生成但格式/编译/精度失败     | 按失败阶段记分并反馈                 | 是             |
| 传输错误、限流、结构不完整的供应端响应 | 相同payload按协议重试，常规2次重试加初次请求 | 否，重试不是新轮      |
| 正常有效响应但实现差          | 内容重试数为0，不重新抽候选             | 当前轮保留         |
| 已有job的轮询超时/断线       | 保存job_id，resume继续轮询        | 否，不重新生成       |
| Harness装配异常         | 保留当前生成输出，修复基础设施后resume     | 否             |
| 额度或账号限制             | 保存状态，恢复后继续或保持未完成           | 否；人工例外须另标     |
| 软件版本明确不匹配           | 停止并审计                      | 不当作普通可比较终态    |

“空输出”不宜统一写成内容失败或统一写成可无限重试：当前结构不合法响应走有限供应端重试；正常API响应但正文为空/length和历史人工结案需看具体生成、请求与状态记录。

### 8.3 终态缺少环境字段：历史重提和当前fallback

最初严格路径会因缺少环境信息停止。恢复辅助函数可封存原receipt/result/status，在相同模型输出、相同工程下做一次基础设施重提，不增加模型轮次。当前`evaluate_round()`默认允许对“环境字段缺失”形成专门0分fallback，**并非所有缺失事件都保证先重提一次**；明确版本不匹配不属于这个缺失字段分支。

本次DeepSeek V4 Pro发现3轮`platform_fallback=true`、3个基础设施重提记录及`environment.status=fallback_zero_missing_environment`。它们以`score_source=platform_result_fallback_zero`记0进入现有统计，不算环境正常核验通过，也不应仅凭0分归因为编译错误。

九模型1080轮中，29轮未提交五文件；其余1051轮有平台结果，其中1048轮环境matched、3轮为上述缺失字段fallback。原结果保留，解释与统计审计应单列这些例外。

## 九、计分、聚合与容易误读的指标

### 9.1 每轮分数

常规有效平台结果采用平台返回的`result_score`和分项，不由Harness根据“代码看起来正确”自行打分。不可恢复格式失败由Harness记0；环境元数据fallback按上一节专门记0并标来源。

本地CANN-Bench评分实现中，编译、功能、性能权重为0.2、0.3、0.5。常规逐用例性能项：

`q_i = (T_baseline - T_HW) / [(T_candidate - T_HW) + (T_baseline - T_HW)]`

常规单算子总分：

`100 × [0.2×编译通过指示 + Σ_i 精度通过指示_i×(0.3+0.5×q_i)/N]`

需要对照实际平台revision解释特殊分支：无NPU性能、无效/缺失锚点和异常终态等。当前本地实现不把性能项统一截到1，因此“永远严格0–100”不是可直接保证的性质。

**总分、精度通过数和speedup是不同量。** 部分正确实现可能有高于某个全正确实现的总分；最高分轮不必是全正确轮。原基准的`operator.avg_speedup`也不是实际宿主端到端速度。

### 9.2 正式主聚合

记第t条轨迹第r轮分数为S(t,r)：

- 轨迹成绩：`B_t=max_r S(t,r)`，只使用完成R1–R5的轨迹。
- 算子成绩：`(B_1+B_2+B_3)/3`，三条完整后报告正式算子均值。
- 波动：三条最佳分数的样本标准差，分母为3−1；可附中位数和范围。
- 模型宏平均：八算子均值等权平均；仅比较九个完整模型。
- 最终轮分数：诊断是否回退，不替代轨迹最高分。

候选筛选使用原始分数精度，最高分并列选较早轮。旧CSV通常四舍五入到六位，精确排序回查原始结果。不能把三轨迹视为大量重复样本来宣称微小差异显著。

### 9.3 需要分别定义的成功率与回退

| 名称            | 定义                        |
| ------------- | ------------------------- |
| 全正确轮次比例       | 全部正式轮次中，平台成功且20/20的比例     |
| 曾全正确轨迹比例      | 一条五轮轨迹中至少一次全正确            |
| 最佳版本全正确比例     | 只看轨迹总分最高轮的精度，不回头挑别轮       |
| 非零轨迹比例        | 五轮最高分大于0，不等于全正确           |
| best-so-far曲线 | 截至当前轮的最高分；它单调不降是定义决定的     |
| 总分回退          | 某轮分数低于此前最高分；不同于只比较相邻轮     |
| 正确性回退         | 首次全正确之后出现非全正确记录；不要求总分同时下降 |

首次编译、首次非零、首次全正确也不能互换。当前部分汇总函数使用终态启发式近似首次编译成功，正式分析应以平台编译分项和结果确认，不凭零分或job名字完成归因。

### 9.4 旧CSV分类脚本的局限

`package_v3_data.classify()`存在简化规则：`submitted=false`先归format_failure；0分且correctness_failed归device_exception；其余0分归compile_failed。这是打包标签，不是根因证明。

两个具体风险：本轮复用旧结果却没有新回执，可能被误归格式失败；平台环境fallback等0分也可能被误解释为编译/设备代码失败。正式论文应优先检查`status=round_completed`、`evaluation_reuse`、`score_source`、环境与平台原结果，再解释分类；本次不修改汇总脚本或重写旧CSV。

## 十、归档、来源可信性与如何复核

内层项目根目录为`PUBLIC_WORKSPACE/cann-bench-master`。正式数据位置由`model_eval/package_v3_data.py`的`MODEL_WHITELIST`限定，不能直接扫描所有历史目录。

单轮常见结构：

```text
model_eval/runs/feedback_experiments/<批次>/<provider>/<模型>/level1_<算子>/trajectory_00X/round_0X/
├─ request_messages.json / request_prompt.txt   精确发送给模型的内容
├─ request_metadata.json                       请求设置、版本与提醒标志
├─ model_output.txt / raw_response.json        聚合输出、响应和用量
├─ generation_status.json                     生成耗时、重试和结束原因
├─ change_summary.json / parse_report.json    简述、严格/可恢复格式结果
├─ parsed/                                   机械提取文件，部分历史目录可能不全
├─ assembly_manifest.json                    输出、骨架和提交工程哈希
├─ submission_project/                       实际提交工程
├─ submission_receipt.json                    提交信息和job_id，可能含敏感字段
├─ benchsite_result.json                      平台完整终态及逐用例结果
├─ environment_verification.json              环境核验／fallback状态
├─ evaluation_reuse.json                      若存在，表示沿用旧结果
├─ feedback_payload.json / feedback_prompt.txt 给下一轮的机械反馈
└─ status.json                               当前轮状态、分数和score_source
```

R5没有后续模型请求，因此可没有feedback_prompt；未提交轮没有平台结果和环境记录是正常情况。记录缺失需结合阶段判断，不能一概认为“代码没了”或“实验没跑”。

已做过的候选审计发现Kimi GELU T2/R3、Qwen GELU T1/R2的本地输出/parsed与实际提交工程存在差异；提交工程目录哈希与原manifest吻合，两份导出以该提交工程为准。不能把现存任意model_output直接当成已评测源码。应结合原始输出哈希、提交工程哈希和归档记录建立来源。

快照核验：初始提示、协议、反馈模板、平台snapshot、源码和提交工程的哈希只能支持对应对象未变；不能单凭某个“V3”标签或一个全局hash声明所有历史请求相同。辅助调用配置和额外提醒仍以精确请求为准。

向外部ChatGPT提供本说明即可先讨论流程；不需要上传账号密钥、鉴权配置或完整提交回执。若提供案例，选必要的去敏请求、源码与错误，保留批次/轮次关联。

## 十一、已有数据能回答哪些问题

1. 在实际调用配置与固定预算下，各模型的完整实现交付质量和跨轨迹稳定性。
2. 五轮中首次正确的覆盖怎样扩大，哪些轨迹仍失败。
3. 已正确之后的总分与性能变化，以及后续回退。
4. 从日志、源码和输入条件中得到哪些可复核的失败或改善解释。

2026-10-14对九模型完整主集合的逐轮核查表明：28条首轮全正确、102条五轮内曾全正确；R1–R4已全正确的95条中，后续最佳全正确总分增量中位数0.986分，65条后来出现非全正确记录。这些是现有统计，不是协议预先保证的结果。

首次正确覆盖、最佳值和回退一起报告，比只看单调的best-so-far更能反映过程。正确后性能变化应使用全正确轮比较，并说明性能统计有效分母和测量波动；不能根据一分增量直接推算百分比加速。

该设计没有证明理论优化极限、最优预算分配或反馈相对独立采样的因果收益。真实多模态模型可用性、质量和效率由已完成的第二部分应用实验分别检验，不能仅从本节的基准结果推断。
